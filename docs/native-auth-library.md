# Native owner authentication: Better Auth source review

Research snapshot: 2026-10-10. No application/dependency changes, provisioning, or live deployment.
Inspected published tarballs in `/tmp/cogitator-auth-research`; findings below refer to **1.7.7**, not an assumed older API.

## Recommendation and scope

**Conditional go for a local protected-mode increment using `better-auth: "1.7.7"`; not a public-deployment approval.**
Use its password hashing, TOTP, recovery codes, signed cookies and SQLite sessions; add application authorization policy, not another authentication implementation.
Mandatory per-session MFA is **not built in**: `user.twoFactorEnabled` is enrollment state and cannot authorize application requests.
The supported session-create hook can record server-only assurance; the precise restricted flow below avoids promoting old password-only sessions.
Runtime regression proof remains a release gate. No competing library is necessary on current source evidence.
Keep existing opt-in/local no-auth mode separate. Owner-only Unix-socket classic MCP access would be a separate local OS capability, not a browser-session bypass on TCP.
Do not expose that socket to remote workers; validate filesystem permissions/ownership and reject browser-accessible bridges. Native auth does not supply execution isolation or remote automation authorization.

## Version, maintenance, compatibility

- npm `latest` and GitHub latest release both identify **1.7.7**, published 2026-09-30; npm package license is **MIT**. Pin exactly and commit a resolved lockfile when implementation is authorized. [1][2]
- The package declares **no `engines` field**; do not misquote this as unrestricted Node support. React peer range is `^18.0.0 || ^19.0.0`. Core dependencies include matching `@better-auth/core` and Kysely adapter `1.7.7`, but other transitive ranges float. [1]
- Cogitator's Node `>=22.19.0`, React 19 and better-sqlite3 stack fit the declared integration. Registry snapshots of current Kysely 0.29.6 (`node >=22`), noble hashes/ciphers 2.4.0 (`>=20.19`) and nanostores 1.5.5 (`^20 || >=22`) fit; these are not a resolved/tested lockfile. [1][3]
- Actively maintained, but **not “no known vulnerabilities.”** 1.7.7 fixes critical Magic Link account takeover, OAuth Proxy confusion and adapter concurrency issues. Published advisory GHSA-fmh4-wcc4-5jm3 still lists `better-auth >=1.6.14` affected for organization invitations. Organization/social/magic-link/SSO plugins are out of scope and must remain absent. [2][4]
- Earlier advisory GHSA-xg6x-h9c9-2m83 specifically concerned cookie-cache MFA bypass; patched long before this pin, but reinforces disabling that cache. Recheck advisories and the resolved dependency graph before shipping. [4]

## Exact supported integration and bootstrap APIs

- `import { betterAuth } from "better-auth"`; configure `database: new Database(authDbPath)` using `Database` from `better-sqlite3`. The built-in Kysely adapter recognizes better-sqlite3; no ORM/server database required. Prefer a separate private auth SQLite file. [5][6]
- `import { toNodeHandler, fromNodeHeaders } from "better-auth/node"`; `toNodeHandler(auth)` accepts Node `IncomingMessage`/`ServerResponse`. `auth.handler(Request)` is the Fetch alternative. Do not consume the body before handing it to the adapter. [7]
- React: `createAuthClient` from `better-auth/react`, `twoFactorClient` from `better-auth/client/plugins`; server plugin `twoFactor` from `better-auth/plugins`. UI state is never authorization evidence. [1][8]
- **Migration import is `better-auth/db/migration`, NOT `better-auth/db`.** `const plan = await getMigrations(authOptions)` returns `toBeCreated`, `toBeAdded`, `toBeAddedIndexes`, `unsafeChanges`, `schemaProblems`, `compileMigrations(): Promise<string>`, `runMigrations(): Promise<void>`. [9]
- Include all plugins/additional fields/database rate limiting in that same options object before generating schema. Inspect compiled SQL/schema problems; backup database, migrate offline, then serve. Required columns without defaults on populated tables raise `UnsafeMigrationError` by default; this is not a general destructive-schema migration engine. [9]
- Core tables are user/session/account/verification; twoFactor adds user.twoFactorEnabled and a twoFactor table (secret, backupCodes, userId, verified, failedVerificationCount, lockedUntil). Database rate limiting adds rateLimit. MFA secrets/codes are encrypted by the plugin by default; protect/persist Better Auth's secret separately from backups. [8][10]
- Simplest offline provisioning: a **CLI-only, non-listening** Better Auth instance with email/password enabled and `disableSignUp: false`, then `auth.api.signUpEmail({ body: { name, email, password } })`. The production instance sets `disableSignUp: true`. Direct API calls do not bypass that flag; ignore bootstrap response credentials and delete its session before serving. [11]
- Alternative confirmed API: CLI-only `admin()` plugin and `auth.api.createUser({ body: { email, password, name } })` **without `headers` or `request`** permits offline creation and uses library password hashing; supplying either without an authorized session is rejected. This requires admin schema fields, so prefer the first option unless needed. Do not expose admin endpoints. [12]
- Neither API enforces “only one owner.” CLI must take an exclusive bootstrap lock/check empty owner DB, persist the one owner ID, fail closed on repeats/partial setup, and serialize against a running server. Runtime must authorize that exact ID, not any authenticated user/email. No real provisioning was performed here.
- HTTP must use an explicit method/path allowlist **before** the generic handler; reject encoded/duplicate-slash/path aliases consistently. Signup remains disallowed even during enrollment. No social/signup/admin/reset/disable-2FA/OTP routes should become reachable by default. [11][13]

## Actual 2FA flow and the assurance seam

1. `enableTwoFactor` (`POST /two-factor/enable`) requires a session and password by default. Restrict body to `method: "totp"`; leave `skipVerificationOnEnable` false and `allowPasswordless` false. It stores encrypted secret/codes with `verified: false` and returns `{ method, totpURI, backupCodes }`; **no MFA approval yet**. [8]
2. `verifyTOTP` (`POST /two-factor/verify-totp`) first calls `verifyTwoFactor`: an existing DB session takes precedence over the temporary challenge cookie. With an existing enrollment session, successful cryptographic verification enables the user, creates a replacement session (passing the old session as override), sets its cookie, deletes the old token, and marks the factor verified. [14][15]
3. Crucial wrinkle: its final `valid()` for an already authenticated session returns the **original** captured session token/user, even though enrollment may have rotated the cookie. Do not identify the resulting session by this JSON token or promote sessions by user ID. [14][15]
4. Later `/sign-in/email` first creates a credential session. The twoFactor after-hook, if enrolled and not trusted, clears its cookies, deletes that session, resets `newSession` to null, stores a verification challenge plus attempts row, and issues a signed temporary two-factor cookie (default 600 seconds). The JSON response is `{ twoFactorRedirect: true, twoFactorMethods }`, not a full session. [8]
5. With **no active session**, successful verify-totp/verify-backup-code consumes that temporary verification via `consumeVerificationValue`, then `createSession`, then sets the signed full-session cookie. Backup `disableSession: true` skips this finalization; reject that option in Cogitator. [15][16]
6. **Supported server-only field:** `session.additionalFields.mfaApproved = { type: "boolean", required: true, defaultValue: false, input: false, returned: false }`; migrate it with the library. `databaseHooks.session.create.before(session, context)` returns `{ data: { ...session, mfaApproved } }`; the library merges this before insertion. It receives actual endpoint context (nullable). [17][18]
7. Safest minimal policy: default/force false for every creation; set true **only** when the creation context path is `/two-factor/verify-totp` or `/two-factor/verify-backup-code` **and `context.context.session` is absent**, with exact owner ID and restricted endpoints. Source shows these challenge-flow `createSession` calls occur only *after* valid factor verification and challenge consumption. Enrollment rotation has an existing session and remains false. Do not infer approval from path in a general before-hook (it runs before verification). [14–18]
8. **Deliberate UX simplification:** after enrollment verification, sign out and sign in again, then complete the temporary MFA challenge. Do not promote the enrollment session at all. Pre-enrollment sessions stay false forever, even when the user's flag flips. Reject recovery verification from any password-only enrollment session; recovery must follow verified enrollment and a fresh password challenge.
9. Gate every protected request on freshly loaded DB session, unexpired token, exact owner ID, and **that session row's** mfaApproved. If response filtering removes this private field, read it server-side by the validated session ID; never set `returned: true` merely for client convenience. `input: false` prevents ordinary input, but the create hook must still override copied fields explicitly. [17][18]
10. Enrollment secret endpoints need narrower authorization than ordinary app access: only a server-selected owner enrollment-session ID can enable/read the pending secret. Serialize this selection; deny other password sessions. Block get-totp-uri once enrolled and disable/re-enable paths; recovery regeneration needs an explicitly MFA-approved session plus password. The library alone allows any valid session + password. [8][14][16]
11. User `hooks.after` runs **before plugin after-hooks** in this pin; it cannot safely approve based on sign-in `newSession`, or sanitize the final twoFactor response. Use the DB create hook above for assurance and a final response boundary for token redaction. [19]

## Cookies, recovery, revocation and abuse controls

- No documented disable-trusted-device switch in this plugin: reject `trustDevice: true` on verification, do not merely hide a checkbox. Also remove/reject incoming trust-device cookies at the auth boundary (and clear prior trust records/cookies if changing policy); otherwise the sign-in after-hook accepts a valid trusted cookie and skips MFA. The per-session false default is defense in depth. [8][15]
- Force `advanced.useSecureCookies: true` in protected mode over HTTPS, retain HttpOnly/SameSite, host-only cookies and fixed trusted origins/baseURL; never disable CSRF/origin checks. Default cookie attributes include HttpOnly, SameSite=Lax and path `/`. Keep local no-auth distinct from insecure protected cookies. [20]
- Password sign-in, get-session and verification responses can contain session tokens. HttpOnly does **not** remove JSON tokens. Use a same-origin response boundary to return only required status/safe user/session metadata, preserving every Set-Cookie header and errors; do not install bearer-token support. Set sensitive response `Cache-Control: no-store`; exclude secrets/tokens from logs. [11][15][21]
- `session.cookieCache.enabled: false`, a real database, and **no secondaryStorage** yield DB-backed sessions. `auth.api.getSession({ headers: fromNodeHeaders(req.headers), query: { disableCookieCache: true } })` reads authoritative storage and rejects missing/expired sessions; browser cached user state is irrelevant. [21]
- Sign-out/revoke APIs delete DB sessions; other-session/revoke-session endpoints check ownership. Set explicit expiresIn/updateAge policy; `session.disableSessionRefresh` is available for fixed expiration. Existing in-flight work is not automatically canceled. [21][17]
- REST and sensitive file requests require fresh checks before side effects/content; SSE requires initial check plus revalidation before each emission/heartbeat and a closure deadline for expiry/revocation, not just authorization when opened. App must propagate deletion to active streams or re-read before writing. Better Auth has no Cogitator SSE/file guard. Never refresh sessions invisibly forever through polling.
- **One-use recovery is source-confirmed atomic in this pin:** verifyBackupCode reads/decrypts list, removes code, then `adapter.incrementOne` conditionally replaces it with predicates `(id, backupCodes == old encrypted value)`. A loser gets HTTP 409 and does not call `valid()`. SQLite Kysely implementation executes a single conditional UPDATE ... RETURNING, including the predicates on the UPDATE itself. This is not the unsafe read-then-unconditional-write implementation. [16][22]
- Concurrent use of different recovery codes may also conflict; retry with fresh state. A code can be burned before session creation fails: fail closed, but surface recovery guidance. Challenge consumption is also one-use; runtime parallel-request tests are still required. [15][16]
- TOTP verification has no persisted last-used timestep in the inspected flow; do not claim one-use TOTP replay rejection. If that is a hard requirement, this is a concrete additional gate (upstream support or narrowly reviewed replay policy needed). [10][14]
- Set `rateLimit: { enabled: true, storage: "database", ... }`; defaults otherwise depend on production environment and use memory. Plugin defaults are 3 requests/10 seconds on `/two-factor/*`. Challenge attempts default to five; account lockout defaults to ten failures/900 seconds, but account/challenge counters apply to sign-in flows, not existing-session enrollment. Limit enrollment separately. [8][15][23]
- Database rate limiter uses atomic increment/conditional reset and unique-key creation retry in this pin; include rateLimit schema migration and test across restarts/concurrency. Missing trustworthy IP falls back to one shared per-path bucket; disabling IP tracking disables this protection. [23]
- Default IP source is x-forwarded-for. `advanced.ipAddress.trustedProxies` only interprets chains, **cannot authenticate the direct sender**. For direct Node ingress overwrite a dedicated IP header from socket.remoteAddress and configure only that header; behind a proxy require an origin restricted to that proxy and header sanitization. `advanced.trustedProxyHeaders` governs forwarded host/protocol separately; use fixed baseURL and leave it off unless justified. [17][24]
- Return TOTP URI/recovery plaintext solely to selected owner enrollment session; render QR locally or provide manual secret entry. Never send URI to a QR website, analytics, logs or third-party scripts. Encrypted storage does not make exposure to the wrong browser safe.

## Required proof / unresolved high-impact edges before implementation acceptance

- Exercise the create-hook context and persisted private field on this exact pin: signup, password-only login, enrollment rotation, failed TOTP, challenge TOTP, recovery, stale pre-enrollment cookie and later user-flag changes. Assert no old session gains assurance and no token appears in browser JSON.
- Concurrent recovery redemption across independent challenges must produce at most one full session; test factor failure/challenge consumption/session creation faults and database contention. Prove rate limiting survives restart and cannot be evaded by client headers.
- Test cookie attributes, CSRF, allowlist normalization/body-option rejection, offline bootstrap race/partial failure, session expiry/revocation across REST/files/SSE, and schema migration from populated state. No runtime harness or dependency installation was executed during this research.
- Local protected delivery can proceed only with these tests; public deployment remains blocked on remote execution/workspace isolation and remote automation design, irrespective of successful auth tests.

## Addendum: offline recovery and replay-hook feasibility (source only)

- CLI-only, non-listening instance: `emailAndPassword: { enabled: true, sendResetPassword: async ({ token }) => { capturedToken = token; }, revokeSessionsOnPasswordReset: true }`; capture in process memory only, never send/fetch the generated URL or log token/password. Keep production reset routes blocked and omit delivery callbacks there; no admin plugin is needed.
- Call `auth.api.requestPasswordReset({ body: { email } })`, require capture for the exact persisted owner, then `auth.api.resetPassword({ body: { token: capturedToken, newPassword } })`; no request/headers/redirect/browser callback needed. Resolve the owner before requesting; the request deliberately reports success for unknown email. Use no background-task handoff; clear the capture afterward. `resetPasswordTokenExpiresIn` controls token lifetime.
- `resetPassword` validates length, consumes `reset-password:${token}`, hashes with the configured library password hasher, creates/updates the credential account, calls optional `emailAndPassword.onPasswordReset`, then revokes sessions if configured. These are sequential operations, not one encompassing transaction: a consumed token stays burned if hashing/write/callback fails; a throwing callback prevents the later revocation. Password reset does NOT reset MFA.
- Complete owner MFA reset requires an offline exclusive maintenance window (server/workers stopped): set `user.twoFactorEnabled = false`; delete every owner `twoFactor` row, removing secret, backupCodes, verified, failedVerificationCount and lockedUntil; delete every owner session, including enrollment/password/MFA-approved sessions. Invalidate app enrollment selection/assurance references and active connections before restart.
- Also invalidate all owner verification capabilities: `2fa-<random>` challenges (`value = ownerId`), their `2fa-attempts-${challengeIdentifier}` counters, `trust-device-<random>` records (`value = ownerId`), and outstanding `reset-password:<token>` records (`value = ownerId`). Do not merely delete `verification.value = ownerId`: attempt counters have numeric-string values and orphan counters can remain after challenge consumption.
- If OTP was ever enabled, clear `2fa-otp-${challengeIdentifier}` and session-bound `2fa-otp-${ownerId}!${sessionId}` records too. Cookies held by clients cannot be remotely erased, but deleting their backing records invalidates capabilities; reject trust cookies at ingress as already required.
- Simplest safe policy for this dedicated single-owner auth DB is deleting ALL verification rows in the same cleanup transaction, including expired/orphan rows. Otherwise cleanup must understand identifier storage (`verification.storeIdentifier` can hash identifiers), related rows and any historical plugins; prefix-only SQL is not generally safe. Preserve account/owner identity; preserve replay reservations or explicitly retire their factor-generation namespace rather than reopening replay windows.
- `auth.api.disableTwoFactor({ body: { password }, headers })` exists but requires a sensitive authenticated session; it rotates only that session and clears only the presented trust record, not all sessions/challenges/trust records. It is not offline owner disaster recovery. No complete supported atomic owner-MFA-reset endpoint was found: pinned schema-aware transactional cleanup (SQL or adapter) is needed for all-or-nothing cleanup, not an admin plugin. Do not claim the password-reset API participates in that transaction; keep maintenance fail-closed across partial failure/retry.
- Source-confirmed challenge TOTP ordering: `createOTP(...).verify(ctx.body.code)` succeeds → failure counters reset → `valid(ctx)` consumes challenge → `internalAdapter.createSession` → `databaseHooks.session.create.before(data, context)` → adapter insertion. The endpoint body is not replaced in this chain; `context.body.code` is the verified submitted code, NOT a returned matched timestep. Require exact owner/path and absent `context.context.session`; enrollment rotation is a separate existing-session path and must remain unapproved.
- `consumeVerificationValue` encloses lookup/consumeOne/duplicate deletion in its own `runWithTransaction`; that scope ends before createSession. `createWithHooks` calls the before-hook before insertion and adds no encompassing transaction. Factor updates, challenge consumption, app replay reservation and session insertion must not be described as one cross-library transaction.
- At the eligible create-before hook, atomically reserve a keyed digest of owner + factor generation + submitted TOTP in app-owned storage, with uniqueness and retention covering the full accepted validity window; reject duplicates/storage failure before approval. Commit reservation independently BEFORE returning approved data; if insertion/cookie issuance later fails, leave reservation and challenge burned. Never persist/log raw codes; this conservative policy may reject a coincidentally repeated code and does not reveal the matched timestep.
- Runtime gates remain: actual context/body/private-field behavior, adapter transaction support, parallel digest/recovery contention, exact OTP acceptance-window/retention bounds, insertion-fault reservation persistence, password-reset failure/retry, cleanup crash recovery and stale-cookie/challenge rejection. No runtime proof or application/dependency changes were performed here.
