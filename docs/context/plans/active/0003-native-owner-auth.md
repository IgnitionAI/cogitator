# Native owner authentication — implementation design

Status: the bounded local native-auth increment is **implemented, independently re-reviewed and locally verified** on 2026-10-10. Final Standards/Spec reviews have no blocking findings; builds, 140 tests and six real TLS/browser journeys pass on Node 26.10.0 and clean Node 22.19.0. See the [verification record](../../../native-auth-verification.md) for evidence and limits. This does not accept public deployment or the complete P1–P5 scope; the work remains uncommitted/unpublished.
Baseline: `8d137e7`, Cogitator 0.3.0. Date: 2026-10-10.

## Understanding lock and scope

The owner explicitly confirmed this replacement for the previously proposed infrastructure login:

- Authentication belongs to Cogitator and travels with the product, independently of the eventual VPS.
- Exactly one owner; no public registration or multi-user/team management.
- Native login, secure sessions and mandatory MFA, covering REST, sensitive files and both SSE feeds.
- An established library supplies password hashing, factor verification, recovery codes and signed sessions; no homemade cryptography/authentication framework.
- No mandatory Authelia, external identity account, SMTP, social login or managed gateway.
- Preserve the current French/English application and trusted local mode for existing installations.
- Firetower deployment and its admin-inventory handoff are suspended; do not run or modify its identity services.

The preceding oneshot authorization permits conservative planning defaults without repeated questions. Authentication is not execution isolation: the Durable, worker, approval, budget, restore and deployment gates in Plan 0002 remain outstanding.

### Assumptions / non-functional defaults

One owner may use multiple browsers. One server process/data home is the supported operating topology; no HA or cross-host writers. Target ordinary protected REST p95 remains under 500 ms on a representative eventual host (not asserted from local tests). MFA/password operations are separately bounded and rate-limited. Existing local operations should remain compatible without secret migration into presets or transcripts.

Protected mode uses a fixed HTTPS external origin behind a trusted TLS terminator, while preserving loopback TCP binding. Native authentication stores are private to the controller OS user and require encrypted off-host backup later. Sessions are database-backed, fixed lifetime (default 24 hours, no indefinite refresh); enrollment sessions are short-lived (default 10 minutes). Revalidation/deletion closes streams within 60 seconds; logout does not abort running work. Pin library versions and review migrations/advisories deliberately.

Cogitator must not inject private authentication configuration, passwords, TOTP seeds, recovery codes or session tokens into logs, URLs, browser persistent storage, model prompts or spawned preset snapshots. Plaintext TOTP enrollment/recovery material is displayed only during authorized owner setup, and should be saved offline by the human. The trust of classic local same-UID processes is explicit: they can already read owner files, so this increment does not claim to contain malicious local agent code. Remote workers cannot inherit that trust; P2 isolation is mandatory before public remote operation.

## Choice and rejected alternatives

1. **Selected and locally verified:** Better Auth **1.7.7**, its two-factor plugin, the existing better-sqlite3 dependency, and a small Cogitator authorization boundary. See [version-pinned research](../../../native-auth-library.md).
2. **Rejected for this requirement:** a separate Authelia/OIDC gateway as a product prerequisite. It adds hosting/enrollment/mail dependencies the owner no longer wants.
3. **Rejected:** hand-written password/session/TOTP primitives. Also avoid an OAuth-focused framework requiring a custom MFA subsystem when the selected library already supplies one.

The known organization-invitation advisory is not dismissed: organization, social, magic-link, admin and SSO plugins/routes are not enabled or exposed. Recheck the resolved graph before acceptance; do not claim the whole package has no vulnerabilities.

## Backend and state boundary

Use a separate private auth directory/database under COGITATOR_HOME, with persistent library secret and public-origin configuration; do not change conversation/history storage or the existing catalog schema. Directory ownership and 0700, secret/database/sidecar permissions and symlink handling are acceptance criteria. Run supported migrations offline using `better-auth/db/migration`, never an implicit destructive schema upgrade on an active server.

`cogitator auth init --origin <https-origin> --email <owner-email>` is an offline, non-serving bootstrap. Password is entered twice through a hidden terminal prompt, never arguments/environment. Dispatch this command before catalog initialization, agent seeding, cron or pool creation. A CLI-only library configuration permits account creation; runtime configuration disables signup. Enforce one owner with a database-side invariant and persist its exact ID. Delete bootstrap sessions before serving. Initial factor setup additionally requires a short-lived high-entropy setup key issued only to the human's interactive local TTY by the offline CLI; retain only its digest. Never put it in a URL, environment variable or log. Password possession alone cannot claim initial enrollment. The capability may resume an expired enrollment claim while valid, but becomes unusable once the factor is verified; offline stopped-server administration can replace an expired/lost key. Serialize initialization against another initializer and an active server; partially created auth state fails closed and must not revert to unauthenticated mode.

Existing installations with no protected-mode indicators remain local. Create a durable `auth-required` marker directly under COGITATOR_HOME before creating the separate auth directory. Either indicator requires valid protected state: removing the whole auth directory still fails closed. A deployed service must also set an explicit authentication-required startup option independently of restored data, so an incomplete/legacy restore cannot silently select local mode. Deliberate removal of all indicators by a trusted administrator is outside this automatic detection guarantee; no disable command is provided. The new implementation must reject unauthenticated requests if its local-mode instance observes a subsequently created required marker. This cannot retrofit unchanged old binaries: upgrading/bootstrap requires the operator to stop and verify all previous instances for this data home, including custom ports, before creating indicators. Checking the configured port is additional protection, not evidence about unknown old processes. Test new-version refusal and configured-port contention; record actual supervisor/process shutdown evidence at deployment. Require stopped-server administration for origin changes, owner recovery and migrations.

Authentication routes use an exact method/path allowlist before the library handler and before generic app/static routing. Reject ambiguous encoded/slash aliases, unexpected fields, oversized/non-JSON mutations, hostile/missing Origin on browser mutations and unrecognized Host. Preserve every Set-Cookie header, but project browser JSON to safe status/user data rather than exposing library session tokens. Disable cookie session caching and forwarded-host/protocol trust. Derive a dedicated rate-limit IP header from the actual socket, never trust arbitrary incoming forwarding headers; behind a single loopback proxy this initially gives shared bounded buckets, not an invented verified client IP.

Public routes: minimal authentication/liveness status and the exact static login shell/build assets needed to render it. `/api/health`, arbitrary static files/SPA fallbacks, workspace files, history and APIs are not public. Harden real-path containment for served assets. Re-check identity before side effects or returning content after asynchronous work. SSE uses fresh session checks at connection and before emissions/heartbeats, with bounded closure on expiry/revocation and cleanup of listeners.

### Per-session MFA, not an account checkbox

The real pinned source establishes an assurance hook: a server-only `session.mfaApproved` field, always forced false unless `databaseHooks.session.create.before` runs after successful temporary-challenge verification on the TOTP/recovery endpoint, with no existing session and the exact owner ID. This must be demonstrated with real-library tests before reliance.

A password-authenticated, unenrolled owner session can access **only enrollment actions**, never application data. Select one enrollment session atomically and bind pending seed access to it; other password sessions cannot overwrite/read that setup. The claim has a bounded lifetime tied to the short session and clears on logout/expiry. A valid setup key permits reclaiming only an expired/revoked claim, not stealing a live one. Give an actionable retry/recovery message rather than a permanent lock. Restrict enrollment to TOTP with password confirmation; no passwordless enable, public reset or factor-disable route.

Successful enrollment rotates only a restricted session. Deliberately sign out and require a fresh password + MFA login afterward; do not promote enrollment or other earlier password sessions. Account `twoFactorEnabled` changing must never upgrade an old session. Suppress/reject trusted-device options/cookies. Only validated DB session + exact owner + enrolled factor + that session's private assurance field authorizes the application.

For normal TOTP login, prevent the same accepted code from creating two full application sessions within its acceptance window: reserve a keyed digest with a single conditional SQLite operation at the successful challenge-session creation seam, retaining it conservatively for five minutes. Atomicity covers that unique digest claim only, not a transaction shared with the library's later session insert. A losing concurrent claimant cannot create an approved session. A committed claim remains consumed across restart/insertion failure; prove the real transaction context and verified code availability before enabling this path. The library remains responsible for cryptographic TOTP verification; do not implement another verifier. Enrollment creates no full application session. Failure may consume a challenge without granting access; clearly request a new login/code. Prove this seam, concurrent attempts and failure handling rather than assuming a before-hook is after verification.

If enabling the pending factor succeeds but its response is lost, the selected session can explicitly regenerate pending setup material; old material then becomes invalid. If the verification response is lost after factor activation/session rotation, return to password login and use the authenticator that supplied the successful code, not the old enrollment cookie; recovery-code regeneration is available after fresh full MFA. Fault-test the library's intermediate factor/user/session updates; inconsistent partial state fails closed into privileged offline recovery, never automatic approval or an endless enrollment loop.

Recovery codes use the library's encrypted storage and conditional atomic redemption. No `disableSession` or trusted-device option is accepted. Display codes only to the selected enrollment session; replacing codes requires full MFA plus password. A lost-code/failed response must have a safe retry or regeneration path. Privileged offline recovery must retain protected mode and revoke sessions/challenges; it must never temporarily enable anonymous access or issue an MFA-approved browser session. Provide a tested stopped-server recovery operation/procedure: reset the password using library-supported hashing/reset APIs, revoke sessions/challenges, clear factor state and enrollment claims, and issue a new setup key, all while keeping the durable protected-mode indicators. Pinned source identifies CLI-only `requestPasswordReset`/`resetPassword` with an in-memory delivery callback and session revocation, followed by schema-aware transactional cleanup of factor rows, all owner sessions and all verification rows in this dedicated one-owner DB. No complete atomic library MFA-reset API exists; this coupling must be version-pinned/tested. Set durable maintenance state before the sequential password reset and retain it through cleanup/key issuance, so a crash cannot restart serving partially reset credentials. Preserve replay reservations. Do not assume library multi-table updates are atomic; interruption must remain fail-closed and rerunnable. If this cannot be demonstrated, recovery is a blocker rather than a documentation-only promise.

### Compatibility without browser-credential leakage

Minimal public liveness prevents the pi extension from mistaking an auth rejection for a dead server. Classic local MCP requires an explicit **owner-only Unix socket** under the protected directory (0600 beneath 0700), not a TCP loopback exemption or an owner browser token.

Both transports must share one route/event setup, forwarding server-owned private request objects through that same handler rather than calling createApp twice. Use native `node:http.request({ socketPath })` for MCP, not a nonexistent standard fetch socket option. The reviewed implementation is now reflected in architecture O4: all TCP remains loopback-only, with this narrowly scoped private Unix IPC listener. ADR-006 likewise clarifies that the single catalog database excludes private authentication state. Mark private-socket requests by server-owned object identity/closure, never by a client header. This is the existing trusted local OS-owner administrative capability, not a grant for remote workers. The shipped MCP adapter is stdio-only (`src/mcp-server.ts`), and extension registration does not introduce an HTTP MCP listener. Verify this remains true, reject browser Origin/Fetch-Metadata headers on the private transport as defense in depth, and prove TCP headers cannot mark a request private. A same-UID operator can deliberately build another bridge; that is outside the trusted local process boundary, not something socket mode bits prevent. No socket mounts/descriptors or browser credentials reach future isolated workers; remote automation still requires Plan 0002's scoped design and deployment must audit for any exposed bridge. Never redirect an explicitly remote COGITATOR_URL to local privileged transport or transmit a local credential to it.

Startup binds/reserves the TCP port before reconciling that instance's stale socket; reject live sockets/unsafe files, avoid unlinking unrelated sockets, and clean up only owned resources. Protected mode is supported on Unix server platforms initially; do not invent insecure named-pipe ACLs for Windows. The default unauthenticated local mode remains unchanged there.

## Frontend contract

Gate App mounting before health/agent fetches or EventSource connections. Reuse the dark interface, Inter/indigo tokens, native accessible controls, LanguagePicker and typed EN/FR catalogs. No third-party enrollment QR/image service; manual authenticator secret entry is sufficient initially.

Operator handoff: stop/verify old instances, finish offline initialization, retain the setup key privately, start the server, and open the configured HTTPS origin. After password login, restricted enrollment explicitly asks for the CLI setup key before exposing pending factor material. LanguagePicker is available before login. EN/FR messages distinguish a live enrollment in another browser (wait for its displayed expiry or resume it), an expired/lost setup key (stopped-server key replacement), and a revoked/expired browser session (fresh login then reclaim only when permitted).

States: loading, local mode, password login, MFA challenge (TOTP or recovery code), restricted enrollment, authenticated app, and explicit setup/network/revocation errors. Prevent duplicate submissions; focus status/error summaries and retain inputs after recoverable errors. Enrollment explains that application access stays locked until a fresh MFA login. Logout revokes only the current browser session, immediately clears its protected views/streams, and explicitly explains in EN/FR that other browsers stay signed in and running work continues. Offline owner recovery revokes all sessions. 401/403 invalidation must not become an infinite reconnect storm. Transient network failures remain distinguishable from revocation.

### Browser HTTP contract for implementation

All paths below are same-origin, cookies only. Mutation bodies are strict JSON; no arbitrary client options reach the library. All sensitive responses are `no-store`, and no response contains a session token.

| Method/path | Request / safe response |
| --- | --- |
| `GET /api/status` | Minimal liveness `{ service: "cogitator", authentication: "local" \| "required" }`; no owner, filesystem or process metadata |
| `GET /api/auth/status` | `{ mode: "local" }` or `{ mode: "protected", state: "anonymous" \| "enrollment" \| "reauthenticate" \| "authenticated", email?: string, expiresAt?: string, enrollment?: { requiresSetupKey: boolean, pending: boolean, busyUntil?: string } }`; dates are ISO strings; email only for a validated owner session |
| `POST /api/auth/sign-in/email` | `{ email, password }` → `{ twoFactorRequired: boolean }`; otherwise refresh status using the cookie |
| `POST /api/auth/sign-out` | `{}` → `{ ok: true }`; current browser only |
| `POST /api/auth/two-factor/enable` | `{ password, setupKey?: string }` → `{ totpURI: string, backupCodes: string[] }`; setup key required unless this is already the selected live enrollment session |
| `POST /api/auth/two-factor/verify-totp` | `{ code: string }` → `{ ok: true }`; enrollment UI signs out afterward; ordinary challenge UI refreshes status |
| `POST /api/auth/two-factor/verify-backup-code` | `{ code: string }` → `{ ok: true }`; challenge only, then refresh status |
| `POST /api/auth/two-factor/generate-backup-codes` | `{ password }` → `{ backupCodes: string[] }`; full MFA only, explicit replacement warning |

Error envelope: `{ error: string, retryAfter?: number, retryAt?: string }` with stable non-secret codes, HTTP status and optional retry seconds/ISO deadline. Frontend localizes the code; never render raw library error objects. Known codes cover invalid credentials/code/input, reauthentication/session required, unavailable auth, setup-key invalid/expired, competing enrollment, rate limits and already-used codes. Unknown codes get a localized safe fallback. A refresh during the temporary MFA challenge may restart at password login; no challenge cookie is exposed to JavaScript. Application 401/403 prompts a status recheck rather than assuming every business denial is logout.

## Acceptance plan

1. Exact-pin library spike: migrations and real sessions; assurance hook for signup/password/enrollment/challenge/recovery; old pre-enrollment sessions denied; no browser JSON tokens; backup-code and TOTP concurrency/replay; failed/faulted verification never grants access.
2. Offline owner initialization/recovery: no public signup, one-owner races, no app startup side effects, hidden credentials, private files, partial-state fail-closed behavior and no silent downgrade.
3. Real HTTP boundary: every REST/files/SSE route, malformed aliases, wrong owner, pre-MFA access, Host/Origin/content-type/body limits, error paths, persistent rate limits/header spoofing, expiry/logout/revocation and listener cleanup. Unauthorized reads must not spawn a pi process.
4. Classic compatibility: default local mode; protected local MCP over the private socket; no TCP bypass; remote URL overrides get no local privilege; extension liveness; snapshots remain secret-free.
5. Browser fixtures over local TLS: login/enrollment/fresh MFA/recovery/logout, inaccessible app before MFA, EN/FR, keyboard, small viewport and network/session failure states. Real-provider/VPS isolation/capacity are separate unproven gates.
6. Independent Standards/Spec code review, full build/tests, and final evidence matrix. Issue #7 stays open while full P0–P5 is incomplete. No VPS changes, new public exposure, release or push implied by this design.

## Decision / review log

- Understanding and native/autonomous approach confirmed by the owner; previous Firetower/Authelia setup is not a current prerequisite.
- Library choice is conditional on actual pinned behavior, not feature-list claims. Enrollment is intentionally followed by a fresh login to avoid session-promotion ambiguity.
- Protected local MCP is an OS-owner capability, not reusable remote-agent authorization. No credentials in snapshots.
- Shared rate buckets and fixed sessions are deliberate one-owner defaults; capacity and broader proxy/client-IP attribution need evidence before expansion.
- Skeptic S1, first-password-holder enrollment: accepted; require an additional private CLI setup capability, without granting application access before MFA.
- Skeptic S2, lost responses/session rotation: accepted; distinguish pending enable retry from verified-factor fresh login, expose full-MFA code regeneration, and require fault-tested offline recovery for partial library updates.
- Skeptic S3, whole auth-directory loss: accepted; separate durable required marker plus explicit deployment mode independent of restored data. No claim of resistance to a trusted root deleting all state/configuration.
- Skeptic S4, browser-accessible local bridges: accepted as a verification gate; shipped MCP is stdio, private transport rejects browser markers, no header bypass, and same-UID arbitrary bridges remain outside containment claims until P2/deployment audit.
- Guardian CG1, old binaries and custom ports: accepted; stopped/verified old-process upgrade is a precondition. New code observes markers; no retroactive enforcement promise for unchanged processes. Configured-port checks are not a global process inventory.
- Guardian CG2, replay reservation atomicity: accepted; only the digest claim is atomic, and verified hook input/transaction context plus conservative consumption across insertion failure are blocking runtime checks. No cross-library transaction is assumed.
- Guardian CG3, recovery API support: accepted; [source addendum](../../../native-auth-library.md#addendum-offline-recovery-and-replay-hook-feasibility-source-only) identifies the reset APIs and unavoidable schema-aware factor/session/verification cleanup. Maintenance remains fail-closed across sequential operations. Recovery fault/runtime proof still blocks acceptance.
- Guardian CG4, IPC versus O4: accepted; proposed explicit TCP-only/O4 clarification, one shared route/event registration, native socket-capable HTTP client, and compatibility tests. No active-contract change before reviewed implementation.
- User Advocate UA1, CLI/browser handoff: accepted; explicit start/open/key-entry sequence, pre-login LanguagePicker, differentiated live-claim/key-expiry/session-expiry messages and journey tests.
- User Advocate UA2, logout scope: accepted; current browser only, other sessions/work continue, explicit EN/FR explanation and stream/view cleanup proof. Offline recovery revokes all sessions.
- [Isolated runtime feasibility](../../../native-auth-runtime-proof.md) passed on 1.7.7: actual migrations, private assurance context, stale enrollment denial, concurrent recovery/replay claims and committed replay reservation after an actual SQLite session-insert failure/reopen. This is not app, rate-limit, bootstrap, recovery-crash, TLS or deployment proof.
- Independent Arbiter disposition: **APPROVED — local implementation only**, 2026-10-10. All ten S/CG/UA objections have explicit substantive resolutions; no remaining design blocker. At that design checkpoint, runtime/product regression, recovery faults, HTTP/TLS, IPC, rate limits, revocation and supported-runtime checks plus independent code review still gated acceptance.
- Final bounded code disposition: **APPROVED — local increment**, after correcting durable logout confirmation, pending-challenge revocation, mutation-time code-replacement authority and enrollment activation/rotation authority. SQLite TEMP constraints guard the real writes; only the activation request's intentional original-session deletion is deferred into final verification/retirement. No transaction spans async library operations. Later interrupted activation stays fail-closed/offline-recovery-only. Independent Standards and Spec re-reviews are clear; the final local runtime matrix passes. O4/O7 and ADR-006 now record the reviewed boundaries.
- Remaining limits are explicit: private-socket interruption before its receipt can require stopped-owner inspection; authentication does not isolate workers; deployment/restore/capacity/soak and the broader P1–P5 gates remain unproven. No public exposure, Firetower action, release or push is authorized by local acceptance.
